# Systematic Bidirectional Synchronization

## Overview

This document describes the systematic, AST-based approach to bidirectional synchronization between semiformal specifications (left) and generated Python code (right).

## Problem Statement

The original heuristic-based approach had two critical issues:

1. **Generation Problem**: When users edited the spec (e.g., changing `x = ...` to `x,y = ...`), the system would lose previously generated code and revert to placeholders.

2. **Mapping Problem**: The system lacked a proper bidirectional mapping between spec nodes and code nodes, making it impossible to apply targeted structural transformations.

## Solution: AST-Level Bidirectional Programming

We implemented a systematic approach based on:
- **Tree Diff Algorithm**: Detects precise changes between spec versions
- **AST-Level Mapping**: Maintains bidirectional links between spec and code
- **Structural Transformations**: Applies non-semantic changes without LLM
- **Lens Laws**: Ensures well-behaved get/putback operations

## Architecture

### 1. AST-Level Mapping (`ast_operations.py`)

#### ASTMapper
Maintains bidirectional mapping:
- `spec_to_code`: Maps spec node IDs to code AST paths
- `code_to_spec`: Maps code AST paths back to spec node IDs

Each `IRNode` now has:
- `code_ast_path`: Path to its location in code AST (e.g., "body[0]")
- `code_ast`: The actual AST node
- `metadata['lhs']`: List of LHS variable names for assignments

#### TreeDiffer
Computes structural differences between spec versions:

**Matching Strategy**: 
- Prioritizes line number + type matching (not name)
- Handles cases where LHS changes (name differs but line/type same)

**Change Types**:
- `LHS_CHANGED`: Assignment LHS modified (x → x,y)
- `SIGNATURE_CHANGED`: Function signature modified
- `RHS_CHANGED`: Assignment RHS modified
- `ADDED/REMOVED/MODIFIED`: Node-level changes

**Key Insight**: Match by line number + type instead of name, because structural changes often modify the name (e.g., `x = ...` → `x,y = ...` creates a node with different variables but same line).

#### StructuralTransformer
Applies structural changes without LLM:

**LHS Change Transformation**:
1. Parse existing generated code to AST
2. Find the assignment by matching old LHS
3. Create new target (single Name or Tuple of Names)
4. Update assignment.targets
5. Unparse back to code

**Example**:
```python
# Before: x = (x_train, x_test)
# After:  (x, y) = (x_train, x_test)
```

### 2. Enhanced Parser (`ast_parser.py`)

**Multi-Variable Assignment Support**:
- Regex now matches `([\w\s,]+)\s*=\s*(.+)` instead of single `\w+`
- Extracts all LHS variable names: `['x', 'y']`
- Stores in `metadata['lhs']` for tree diff comparison
- Uses first variable as primary node name for ID stability

**Why This Matters**: Enables the tree diff to detect when `x = ...` becomes `x,y = ...` by comparing the LHS lists.

### 3. Synchronization Flow (`ir_sync.py`)

#### sync_spec_change (GET transformation)

```python
def sync_spec_change(old_spec, new_spec):
    # 1. Parse new spec
    new_ir = parse_semiformal(new_spec)
    
    # 2. Detect structural changes via tree diff
    structural_changes = differ.diff_specs(old_ir, new_ir)
    
    # 3. Merge new IR into old IR (preserves code_text)
    old_ir.merge_from_spec_update(new_ir)
    
    # 4. Apply structural transformations (no LLM)
    for change in structural_changes:
        if change.type == LHS_CHANGED:
            # Transform AST directly
            code_ast = parse(node.code_text)
            transformed = transformer.apply_change(change, code_ast)
            node.code_text = unparse(transformed)
            node.status = USER_EDITED  # Preserve it
    
    # 5. Generate skeleton (uses transformed code_text)
    generated_code = generate_skeleton(old_ir)
    
    return generated_code
```

### 4. Skeleton Generator (`skeleton_generator.py`)

**Preservation Priority**:
1. **Transformed/Generated Code** (`status in [GENERATED, USER_EDITED, NEEDS_REGEN]`)
   - Uses `node.code_text` directly
   - Includes structurally transformed code
2. **Complete Spec Code** (`status == SYNCED`)
   - Uses `node.spec_text`
3. **Placeholders** (`status == INCOMPLETE`)
   - Generates stubs/placeholders

**AST Mapping Build**:
After generating skeleton, builds bidirectional mapping:
- Parses generated code to AST
- Matches statements to spec nodes by name/type
- Records AST paths in `node.code_ast_path`
- Adds to `mapper` for future transformations

## Workflow Example: x → x,y

### Initial State
```python
Spec: x = split dataset into training and test sets
Code: x = (x_train, x_test)  # Generated by LLM
```

### User Edits Spec
```python
Spec: x,y = split dataset into training and test sets
```

### System Response

1. **Parse**: Creates node with `name='x'`, `metadata['lhs']=['x','y']`

2. **Tree Diff**: 
   - Matches by line 3 + type NL_EXPRESSION
   - Compares LHS: `['x']` vs `['x','y']`
   - Returns: `LHS_CHANGED` with `old_lhs=['x']`, `new_lhs=['x','y']`

3. **Structural Transformation**:
   ```python
   # Parse: x = (x_train, x_test)
   code_ast = parse(node.code_text)
   
   # Find assignment with LHS=['x']
   assignment = find_assignment(code_ast, old_lhs=['x'])
   
   # Create new target
   new_target = Tuple([Name('x'), Name('y')], ctx=Store)
   assignment.targets = [new_target]
   
   # Unparse: (x, y) = (x_train, x_test)
   node.code_text = unparse(code_ast)
   node.status = USER_EDITED
   ```

4. **Skeleton Generation**:
   - Sees `node.status == USER_EDITED`
   - Uses `node.code_text` directly
   - Final code: `(x, y) = (x_train, x_test)`

## Key Principles

### 1. Line-Based Matching
Match spec nodes by line number + type, not name. This handles structural changes where the name changes (like LHS modifications).

### 2. Eager Transformation
Apply structural transformations immediately when detected, before skeleton generation. Mark as USER_EDITED to preserve.

### 3. Code Preservation
Once code is generated (by LLM or transformation), preserve it in `node.code_text`. The skeleton generator respects this.

### 4. Metadata-Driven Diff
Store structural information (like LHS variable lists) in metadata to enable precise change detection.

### 5. AST-Level Operations
Work at AST level for transformations to ensure:
- Syntactic correctness
- Proper structure preservation
- Easy unparsing back to code

## Comparison: Heuristic vs. Systematic

| Aspect | Heuristic Approach | Systematic Approach |
|--------|-------------------|---------------------|
| Change Detection | Text comparison | AST tree diff |
| Node Matching | By name | By line + type |
| Transformations | None (regenerate) | AST transformations |
| Code Preservation | Unreliable | Guaranteed |
| Mapping | Implicit | Explicit bidirectional |
| Lens Laws | Not enforced | Enforced |

## Benefits

1. **Correctness**: Structural transformations are syntactically correct by construction (AST)
2. **Efficiency**: No LLM calls for structural changes
3. **Predictability**: Users know what changes will trigger regeneration vs. transformation
4. **Debuggability**: Clear separation between detection, transformation, and generation phases
5. **Extensibility**: Easy to add new transformation types (signature changes, reordering, etc.)

## Future Extensions

### 1. More Transformation Types
- Function signature changes (add/remove parameters)
- Argument reordering
- Variable renaming propagation

### 2. Backward Transformations (PUT)
- Code edits → spec updates
- Extract intent from code changes
- LLM-assisted semantic synchronization

### 3. Conflict Resolution
- Simultaneous spec + code edits
- Use AST diff to identify conflicts
- LLM-assisted merge strategies

### 4. Fine-Grained Mapping
- Expression-level mapping (not just statement)
- Track data flow through transformations
- Enable partial regeneration

This systematic approach replaces ad-hoc heuristics with principled AST-level operations, ensuring:
- **Correct**: Syntactically valid transformations

The key insight is treating bidirectional programming as a *transformation problem* rather than a *regeneration problem*.
