# Bidirectional Programming Implementation Analysis

## Executive Summary

This is a sophisticated **bidirectional synchronization system** for semiformal programming where:
- **Left side (spec)**: Semiformal Python with natural language descriptions
- **Right side (code)**: Complete, executable Python programs
- **Sync mechanism**: Maintains correspondence between spec and code through an Intermediate Representation (IR)

The system uses lens-based transformations (get/put operations) combined with AST-level mapping and structural transformations to maintain bidirectional consistency without unnecessary LLM regeneration.

## Part 1: IR Structure (Intermediate Representation)

### 1.1 Core Data Models (`backend/ir.py`)

#### **NodeType Enum**
Represents different kinds of program elements:
```
- FUNCTION_DEF: Function definitions
- FUNCTION_CALL: Calls to undefined functions (need stubs)
- VARIABLE_ASSIGN: Variable assignments
- VARIABLE_REF: Variable references
- NL_EXPRESSION: Natural language assignments (x = "split data into parts")
- PSEUDOCODE: Non-Python pseudocode
- STATEMENT: Complete Python statements (e.g., print calls)
- MODULE: Top-level module
```

#### **NodeStatus Enum**
Tracks the generation state of each node:
```
- INCOMPLETE: Needs generation (has ... or NL)
- GENERATED: Generated by LLM
- USER_EDITED: Modified by user on code side
- SYNCED: Complete Python, in sync between spec and code
- NEEDS_REGEN: Signature changed, regeneration needed
```

#### **IRNode Class** (Lines 52-105)
The central data structure representing one program element:

```python
@dataclass
class IRNode:
    id: str                          # Unique identifier
    node_type: NodeType              # What kind of element
    name: str                        # Function/variable name
    status: NodeStatus               # Generation state
    
    # Spec side (left editor)
    spec_location: SourceLocation    # Where in spec source
    spec_ast: ast.AST                # Parsed Python AST
    spec_text: str                   # Original spec text
    spec_signature: str              # Normalized signature
    spec_hash: str                   # Content hash for change detection
    
    # Code side (right editor)
    code_location: SourceLocation    # Where in generated code
    code_ast: ast.AST                # Code's AST node
    code_text: str                   # Generated/edited code
    code_signature: str              # Signature in generated code
    code_ast_path: str               # Path to node in AST (e.g., "body[0]")
    
    # Dependencies
    depends_on: Set[str]             # IDs of nodes this depends on
    used_by: Set[str]                # IDs of nodes using this
    
    # Metadata
    metadata: Dict[str, Any]         # Custom info (is_nl, lhs, rhs, etc.)
```

**Key insight**: Each IRNode maintains BOTH spec and code representations, enabling bidirectional transformations.

#### **Lens Classes** (Lines 108-220)
Implement get/put transformations following lens laws:

```python
class Lens:
    def get(self, spec: str, context: ProgramIR) -> str:
        """Transform spec → code (generation)"""
    def put(self, code: str, spec: str, context: ProgramIR) -> str:
        """Transform code → spec (reverse sync)"""

class FunctionLens(Lens):
    # Handles function definitions
    # get: Generate code from spec function
    # put: Extract intent from code back to spec

class VariableLens(Lens):
    # Handles variable assignments
    # get: Generate expressions from NL
    # put: Preserve NL in spec even when code changes
```

**Lens Laws Implemented**:
- `GetPut: put(s, get(s)) = s` - Applying get then put returns to spec
- `PutGet: get(put(s, c)) = c` - Applying put then get returns to code
- `PutPut: put(put(s, c1), c2) = put(s, c2)` - Last put wins

#### **ProgramIR Class** (Lines 223-556)
Container managing the entire program IR:

**Key Methods**:
1. **`merge_from_spec_update(new_ir)`** (Lines 276-325)
   - CRITICAL for bidirectional sync
   - Detects changes in spec by comparing old and new IR
   - Preserves generated code for existing nodes
   - Updates signatures while keeping implementations
   - Returns: Dict mapping node_id → change_type

2. **`_merge_node(existing, new)`** (Lines 327-353)
   - Checks if signature changed
   - Detects content changes via hash comparison
   - Updates location and metadata

3. **`_handle_signature_change()`** (Lines 355-383)
   - Uses AST manipulation to update code signature
   - Preserves function body when signature changes
   - Marks for regeneration if semantic change

4. **`topological_sort()`** (Lines 430-460)
   - Returns nodes in dependency order
   - Crucial for generation order
   - Ensures dependencies are generated first

5. **`apply_get()` and `apply_put()`** (Lines 462-500)
   - Apply lens transformations to all nodes
   - Process nodes in topological order

### 1.2 Example: The x → x,y Case

Initial spec:
```
x = split dataset into training and test sets
```

Parsed IR node:
```python
IRNode(
    id="nl_expression:x:2",
    node_type=NodeType.NL_EXPRESSION,
    name="x",
    status=NodeStatus.INCOMPLETE,
    spec_text="x = split dataset into training and test sets",
    metadata={'lhs': ['x'], 'rhs': 'split dataset...', 'is_nl': True}
)
```

After LLM generation:
```python
node.code_text = "(x, y) = (x_train, x_test)"
node.status = NodeStatus.GENERATED
node.code_location = SourceLocation(line=8, col=0)
```

User edits spec to `x,y = split dataset...`:
1. Parser creates new IR node with `metadata['lhs']: ['x', 'y']`
2. `TreeDiffer.diff_specs()` detects `LHS_CHANGED`
3. `StructuralTransformer.apply_lhs_change()` updates code AST
4. Generated code preserved: `(x, y) = (x_train, x_test)`

**This is the KEY insight**: Instead of regenerating, we transform existing code.

## Part 5: Code Generation (`backend/skeleton_generator.py` + `backend/diff_generator.py`)

### 5.1 Skeleton Generator (372 lines)

**Purpose**: Generate complete, executable Python without LLM.

#### **`generate()` Method (Lines 37-114)**

Three-phase generation:

```python
def generate(self, ir: ProgramIR) -> str:
    lines = []
    
    # Phase 1: Collect and generate stubs for undefined functions
    undefined_funcs = {}
    for node in ir.nodes.values():
        if node.node_type == NodeType.FUNCTION_CALL:
            undefined_funcs[node.name] = node
    
    for func_name, node in undefined_funcs.items():
        stub = self._generate_function_stub_from_call(node, ir)
        lines.append(stub)
    
    # Phase 2: Generate code for other nodes
    for node in sorted_nodes:
        if node.status.value in ('generated', 'user_edited', 'needs_regen'):
            # Priority 1: Use existing generated code
            lines.append(node.code_text)
        elif node.status.value == 'synced':
            # Priority 2: Use complete spec code
            lines.append(node.spec_text)
        else:
            # Priority 3: Generate stub/placeholder
            lines.append(self._generate_node_code(node))
```

**Key insight**: Preserves generated code by checking `node.code_text` first.

#### **`_generate_node_code()` (Lines 173-229)**

Selects appropriate output based on node type and status:

| Status | Action |
|--------|--------|
| GENERATED | Use `code_text` (preserve) |
| USER_EDITED | Use `code_text` (preserve) |
| NEEDS_REGEN | Use `code_text` (preserve) |
| SYNCED | Use `spec_text` (already complete Python) |
| INCOMPLETE func | Create stub with `...` |
| INCOMPLETE var | Create placeholder with comment |
| NL_EXPRESSION | Create `var = ...  # <nl_description>` |

### 5.2 Diff Generator (521 lines)

Handles LLM generation with context awareness.

#### **`generate_from_ir()` (Lines 88-166)**

```python
def generate_from_ir(self, ir: ProgramIR) -> Tuple[str, List[UnifiedDiff]]:
    # 1. Generate skeleton (preserves generated code)
    skeleton_code = generate_skeleton(ir)
    
    # 2. Get incomplete nodes needing LLM
    incomplete_nodes = ir.get_incomplete_nodes()
    
    if not incomplete_nodes:
        return skeleton_code, diffs  # Nothing to generate
    
    # 3. Build program context
    context = self._build_program_context(ir)
    
    # 4. Generate implementations
    implementations = self._generate_implementations(
        incomplete_nodes, context, ir
    )
    
    # 5. Apply to skeleton
    generated_code = self._apply_implementations(
        skeleton_code, implementations, ir
    )
    
    # 6. Update IR with generated code
    for node in incomplete_nodes:
        node.code_text = implementations[node.id]
        node.status = NodeStatus.GENERATED
```

#### **`_build_program_context()` (Lines 168-226)**

Provides rich context to LLM:

```python

    'dependencies': {...},                   # Dependency graph
    'complete_elements': [...],              # Already complete code
    'generated_elements': [...],             # Already generated code

}
```

**Why full context?** LLM generates coherent code that respects:
- How functions are called (infer parameters)
- What data types flow through (infer return types)
- Dependencies and usage patterns

## Part 6: Edit Handling

### 6.1 Specification Changes (Left Side)

**Workflow when user edits spec**:

1. **Continuous Parse** (fast):
   - Parser creates new IR from spec
   - No code generation
   - Returns incomplete nodes for visualization

2. **Structural Transform** (instant):
   - `TreeDiffer` detects LHS/signature changes
   - `StructuralTransformer` updates code AST
   - Generated code preserved

3. **LLM Generation** (on save/Cmd+S):
   - Only incomplete nodes regenerated
   - Full program context provided
   - Previous implementations shown as examples

### 6.2 Code Changes (Right Side)

**PUT transformation** (not fully implemented):

```python
def sync_code_change(self, spec: str, old_code: str, new_code: str):
    # 1. Detect which nodes changed in code
    changes = self._detect_code_changes(old_code, new_code)
    
    # 2. Apply put transformation to each node
    for node_id, new_text in changes.items():
        node.code_text = new_text
        node.spec_text = lens.put(new_text, node.spec_text, context)
    
    # 3. Return updated spec
    return ir.apply_put(code_changes)
```

## Part 7: Current Architecture Issues & Mapping Problems

### 7.1 Issues Identified

#### **Issue 1: Enum Identity Problems**

Code that fails:
```python
if node.status in (NodeStatus.GENERATED, NodeStatus.USER_EDITED):
    # FAILS: Enum identity comparison
```

This fails when enums are imported from different paths:
- `from ir import NodeStatus` 
- `from backend.ir import NodeStatus`

**Solution** (already applied in skeleton_generator.py line 188):
```python
if node.status.value in ('generated', 'user_edited', 'needs_regen'):
    # Uses value comparison instead
```

#### **Issue 2: Session State Not Preserved**

Previous implementation created fresh IR on each skeleton request, losing all generated code.

**Solution**: Session-based IR management (main.py line 137-198):
```python
def get_or_create_session(session_id: str) -> AutoSync:
    if session_id not in sessions:
        sessions[session_id] = AutoSync()
    return sessions[session_id]

@app.post("/skeleton")
def skeleton_endpoint(request: AnalyzeRequest):
    session = get_or_create_session(request.session_id)
    new_ir = parse_semiformal(request.spec_code)
    
    # MERGE into existing IR (preserves generated code!)
    if session.sync.ir:
        session.sync.ir.merge_from_spec_update(new_ir)
```

#### **Issue 3: Mapping Between Spec and Code**

**Problem**: After generating code, when spec changes, system doesn't know which code corresponds to which spec node.

**Solution**: Bidirectional mapping:
- `spec_location`: Line/column in spec
- `code_location`: Line/column in generated code
- `code_ast_path`: Path in code AST (e.g., "body[5]")

This enables:
- Finding which code to transform when spec changes
- Extracting intent from code when syncing back
- Precise targeted regeneration

### 7.2 Remaining Gaps

#### **Gap 1: Code → Spec Sync (PUT)**
Backward sync from code edits to spec is partially implemented but not integrated into frontend.

**What's needed**:
- Code diff detection (done in `_detect_code_changes`)
- LLM-assisted intent extraction
- Spec update with proper NL annotation
- Visualization of roundtrip changes

#### **Gap 2: Conflict Resolution**
If user edits both spec and code simultaneously, system doesn't detect conflict.

**What's needed**:
- Timestamp tracking for last edit location
- Conflict detection algorithm
- Multi-way merge (spec, code, previous generated)
- User-facing conflict resolution UI

#### **Gap 3: Fine-Grained Mapping**
Currently maps at statement level. Could go deeper:

**Expression-level mapping**:
```python
# Current: node maps to line 5-10 in code
# Better: could map individual function calls within expression
```

#### **Gap 4: Type Inference**
Parser doesn't track or infer types:

```python
x = split_data()  # What type is x?
result = train_model(x)  # Does train_model accept this type?
```

**What's needed**:
- Type annotation extraction from docstrings
- Flow-sensitive type tracking
- Mismatch detection with LLM feedback
